# ИСПРАВЛЕНИЕ решения владельцем — 17.10.2026

**Действующий статус, имеющий приоритет над текстом отчёта за 16.10:** Forecast **v0.4 и v0.6 вновь участвуют в дальнейших испытаниях**. Предыдущее распоряжение «не развивать/не тестировать» отменено. Нельзя считать эти версии запрещёнными методами только на основании предыдущего неудачного исследовательского опыта.

- `v0.4` = `BIRZHA_FORECAST_BASELINE_V0_4_SCENARIOS`, исходный код **main**; `v0.6` = `BIRZHA_FORECAST_BASELINE_V0_6_EVIDENCE_DECISION`, исследовательский код в `codex/g2-baseline-decision-contract-20261010` (не отдельная установленная на HOME модель).
- Статус каждой: **ACTIVE_RESEARCH_UNVALIDATED**; решение **CONTINUE_CONTROLLED_COMPARATIVE_TESTING**. Они восстановлены как кандидаты для сравнения, **не как статистически доказанные прогнозы и не как разрешённые торговые системы**.
- Старые 17 исторически оцениваемых случаев по 5/10/20 сессиям и исходные MAE остаются ровно такими, какими были. Удалять или задним числом заменять Forecast/Outcome запрещено.
- Каждая следующая проверка обязана оценивать **обе версии на одинаковых инструментах, датах, исходных свечах, горизонтах и критериях отказа**, наряду с ориентиром неизменной цены и простой инерцией; любые отсутствующие данные и нейтральные ответы учитывать отдельно.
- **История 2025–2026 пригодна для диагностики; не является доказанно независимой проверкой.** Новые перспективные прогнозы должны быть зафиксированы до будущего события с подтверждённым временем получения данных и точным SECID.
- Формулы и параметры существующих версий на этом этапе **заморожены**; разрешено исправлять установленную техническую ошибку отдельной новой версией и с новой документацией, нельзя подбирать параметры по уже известным исходам.
- Запрет свечного псевдопрофиля как **нового доказательства направления/Control/Route** остаётся методологическим замечанием: для точного воспроизведения V0.4/V0.6 следует отдельно маркировать унаследованную зависимость, не переписывать историю; если исследования требуют отключения признака, это уже **новый именованный вариант**, а не тихое изменение V0.4/V0.6.
- Отдельная развёртка / слияние / изменение допуска `forecast.create` на HOME **не входят** в решение о возобновлении исследования. PR #256 с `approved_only` не является запретом на локальный исследовательский replay, но **включать этот режим без отдельного согласования нельзя**.
- [Карточка возобновлённого сравнительного опыта](G2_REINSTATED_V04_V06_COMPARISON_20261017.md). Единственный источник машинных статусов: `src/birzha/application/method_registry.py` V2.

# Реестр проверенных и отклонённых методов — Биржа MCP (16.10.2026)

**Единый источник машинных статусов:** `src/birzha/application/method_registry.py`, `G2_METHOD_DECISIONS_V1_20261016`.
**После отдельного разрешения на установку** сервер сможет отдавать тот же справочник инструментом `methods.registry`. До этого он доступен только в GitHub Draft PR. Никаких новых таблиц DuckDB для старых методов не создаётся.

## Для чего он нужен

Не копить отработавшие модели как активную «библиотеку стратегий», а вести короткую проверяемую историю решений:
название и версия → исследованный период → сколько пригодных прогнозов → метрика и простой ориентир → решение → причина отказа/допуска → ссылка на протокол → что нельзя автоматически делать с методом.

**Имеется различие между тремя состояниями:**
1. `НЕ ПРИНЯТ ДЛЯ ПРОГНОЗА`: старая комбинация не показала убедительной точности. Не продолжаем подгонять её коэффициенты.
2. `ЗАПРЕЩЁН КАК ОСНОВАНИЕ ДЛЯ НАПРАВЛЕНИЯ`: ненадёжный свечной профиль объёмов — не считать профилем реальных сделок.
3. `ОПИСАТЕЛЬНЫЙ ИЛИ ИССЛЕДОВАТЕЛЬСКИЙ`: технически вычисляется, но преимущество в прогнозе не установлено.

Слова «не доказал эффективность» **не равны** «математически доказано, что признак бесполезен». Индивидуальные SMA, return, ER и ATR **по отдельности** не прошли независимую проверку на этой выборке.

## Фактическое решение по версиям и компонентам

| Метод / признак | Статус дальнейшей разработки | Что делать |
|---|---|---|
| Forecast v0.4 (`BIRZHA_FORECAST_BASELINE_V0_4_SCENARIOS`) | Исторический; не допущен к прогнозу | Не совершенствовать эвристику; хранить версию и отчёт для воспроизводимости |
| Forecast v0.6 (`BIRZHA_FORECAST_BASELINE_V0_6_EVIDENCE_DECISION`) | Исторический; не допущен к прогнозу | Не считать меньшую MAE доказательством точности направления; не развивать старую формулу |
| `CANDLE_TYPICAL_PRICE_VOLUME_PROXY_V1` | **Исключён как направленный фактор** | Не использовать для прогноза направления, Control или Route. Старые свидетельства не стирать |
| SMA20/SMA50, доходности 5/10/20, ER20 | Только описание рынка | Не переносить как самостоятельные BUY/SELL-сигналы без отдельного испытания |
| SMA-TR14 («старый ATR») | Исторический масштаб | Не подменять молча Wilder и не переписывать старые записи |
| Wilder ATR14 + подтверждённые HH/HL, LH/LL + median20 volume (Draft #254) | **25 целевых и 517 общих технических тестов PASS**, но прогноз не проверен | Проверять на новых наблюдениях отдельно; **нет** автоматической интеграции в принятую модель |
| Six-regime Market State (Draft #200) | Неутверждённая исследовательская модель | Методологическая проверка причинности и порогов до первого принятия |
| Раздельные 9 методов `BIRZHA_METHOD_SET_V3` | Диагностика без independent method-level evidence в опыте v0.4/v0.6 | Каждый оценивать отдельно, не переносить вывод всей модели на конкретный признак |
| Неизменная цена | Обязательный простой ориентир | Только сравнение ошибки в тех же случаях, не отдельная торговая стратегия |

При оценке исходов был исследовательский, **восстановленный** архив, а не доказанный исходный поток T0.

- 6 рынков: SBER, Si, BR, GOLD, IMOEX, RTSI.
- 5 фиксированных дат: 31.03.2025, 30.06.2025, 30.09.2025, 30.12.2025, 31.03.2026.
- 30 запланированных случаев, 20 прогнозов, 10 отказов по входам, **17** пригодных для оценки будущих исходов (51 пара на 5/10/20 сессий).
- Доля направленных решений: v0.4 — 7, v0.6 — 5; на пяти общих направленных случаях v0.6 не улучшила направление.
- MAE (процентные пункты): горизонты 5/10/20: v0.4 **3,7704 / 3,3850 / 3,6870**, v0.6 **3,7180 / 3,2797 / 3,3265**, простая неизменная цена **2,9753 / 3,2008 / 3,4534**.
- Отдельной доказанной торговли, выигрыша после затрат, строгой независимой исторической доступности данных **нет**.

## Почему нельзя просто удалить старые записи

Старые методы **не нужны как рабочие методы в новой базе** и не требуют отдельной серверной таблицы, но:
- исторические Forecast Records immutable, Outcome append-only — старые факты расчёта и исходов не удалять;
- старый код и его точная версия в Git истории нужны, чтобы аудит мог воспроизвести причину отрицательного решения;
- заменять упоминания «v0.4» в старом прогнозе «v0.6» или новым именем нельзя;
- добавлять отклонённые методы в новую схему **активного отбора** запрещено без нового preregistered исследования, новой версии и отдельного решения владельца.

## Принцип дальнейшей разработки

1. Новый кандидат получает **собственный ID, версию формулы, ограничения данных и источник**, до просмотра будущих результатов.
2. Разделяем три оценки: **верность направления**, **величина ошибки**, **первый достигнутый ценовой рубеж**; отдельно измеряем количество отказов.
3. Прогноз и версия входных данных должны быть зафиксированы до исходов. Старые reconstructed архивы — **разработка и диагностика**, новые перспективные наблюдения — отдельно.
4. Сравнивать только на **одинаковых датах и инструментах** с неизменной ценой и простым продолжением тренда. Не выбирать «удачные даты» задним числом.
5. Причину каждого недоступного результата (нет входов, rollover, незакрытый горизонт, нарушение источника) фиксировать как отдельный статус, **не считать ошибкой прогнозирования**.
6. Для допусков к новому прогнозу требуются независимая методологическая проверка и новые исходы, а не одна зелёная проверка кода.
7. Никакие новые торговые действия, изменение старого Forecast или изменение HOME не делаются при записи в справочник.

## Важная разница между реестром и текущим работающим кодом

На `main` всё ещё существует Legacy Forecast v0.4 и диагностический `VOLUME_LEVELS`, который может потреблять свечной proxy из `MarketSnapshot`. **Создание реестра само по себе не отключает эти вызовы.**

Нужно отдельное согласованное изменение runtime, чтобы новые прогнозы не выбирали недопущенные эвристики. Оно должно быть проверено на совместимость с существующими MCP tools и журналом, выполнено с явным разрешением владельца на merge/HOME-развёртывание. До этого никакие слова «выведено из активной системы» к реальному HOME не относятся.
