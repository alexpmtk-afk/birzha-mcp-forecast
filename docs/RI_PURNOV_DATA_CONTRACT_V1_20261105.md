# RI / Модель 3 Пурнова — единый контракт исходных данных, v1 (05.11.2026)

Статус: **RESEARCH_ONLY / НЕ УСТАНОВЛЕНО / НЕ ДОПУЩЕНО К ПРОГНОЗУ**.
Это **контракт данных**, а не новая модель, не новый сборщик и не разрешение на записи в рабочие OHLCV.
Первичные источники: живая [Карта проекта — биржа, «модель 3 Пурнов»](https://docs.google.com/spreadsheets/d/1_NGm6oiBF7rUV7TVNjP13huYyK4u8b21oKDOAQThEvQ/edit?gid=1060952643) (87 P3-001…087) и существующий [MOEX_HISTDATA_RI_MCP_CANONICAL](https://docs.google.com/spreadsheets/d/1PuPv7Nv_Dpj-KTECPHNHecj34HrR9K5y53OwRcu7RVY/edit).
Поштучное сопоставление идентификаторов правил и реально существующих полей: [машинный манифест](contracts/ri_purnov_rule_data_manifest_v1.json).

## Назначение

Достроить **один общий архив инструмента RI**, чтобы ПОСЛЕ проверки качества он позволял воспроизводить причинный набор признаков на T0 и анализировать Пурнова по цепочке:
**свеча/спред → объём/усилие → прогресс → удержанный результат → подтверждение/отмена**.
Основной шаг H1, контекст только завершённых D1, вспомогательный M15 и исходный M1. Кандидат на H1 не равен прогнозу/входу.
Другие модели читают общие рыночные показатели, не получают второй архив.

## Что действительно можно получить без новых источников

| Физическое хранилище | Поля / смысл | Ограничение |
|---|---|---|
| `D1/H1/M15` | exact SECID, trade_session_date, bar start/end, O/H/L/C, volume, is_complete, normalized_sha256, source_file_id | available_at пуст; сессии rule-derived; incomplete сохраняется |
| `M1_SOURCE_INDEX` и Drive ZIP | minute begin/end/O/H/L/C/volume, source SHA, контракт/месяц | M1 не содержит цен и сторон отдельных сделок |
| `*_INDICATORS` | range/body/wicks/CLV, ATR, RVOL approx, prior highs/lows, overlap, progress, pivots, structure, wave hints, failed-break candidates | части показателей нет; качество/доступность не аттестованы |
| `SESSIONS/CONTRACTS` | календарь, режим, торговые даты, точные SECID, сроки контракта, T−1 | первичные per-bar TRADEDATE и tick_size/value/multiplier не полностью заполнены |
| `QUALITY_AUDIT/SYNC_STATUS/VERIFIED_RANGES/STORAGE_RULES` | доказательства, ошибки, сохранённая политика, статусы | прежний PASS не означает PIT или готовность к прогнозу |

Ключ будущего набора данных: `(RI, exact_secid, timeframe, bar_start_time, source_version)`.
Ключ T0-расчёта: `(exact_secid, closed_H1_end, calculation_spec_version, source_snapshot_digest)`.
Разделять сырой контрактый ряд, T−1 выбор основного контракта и отдельно утверждаемую непрерывную ценовую координату. Никогда не объединять объёмы контрактов в фиктивную единую свечу.

## Запрещённые подмены и недостающие данные

1. **True Delta** требует идентификации агрессивной стороны/покупок/продаж, либо проверенного биржевого агрегата с определённой семантикой и доступностью. `p3_minute_sign_delta_proxy` — знак изменения close минуты × объём; не true delta.
2. **True Volume-at-Price / POC / HVN / LVN / VAH / VAL** требует проверенного распределения сделок по ценовым уровням. Размазывание M1-volume по всему диапазону минуты — лишь приближение. У существующих `p3_profile_*_approx` статус APPROX; без сделок **не** повышать точность метки.
3. **PIT**: время появления исторических исходников **не известно**. `available_at=bar_end_time` запрещено как исторический факт. Для нового поступления данных сохранять реальное время публикации/первого получения и receipt; для прошлого явно UNKNOWN.
4. **Сессии и полнота**: сверить официальный календарь/TRADEDATE и аномальные 402 H1, M15 incomplete, 1711 SHA и 4 D1/H1 расхождения. Не объявлять 15 без наблюдений полностью торгованными минутами и не заполнять отсутствующее нулём.
5. **Прогнозные состояния**: готовая `p3_candidate_state` — метка исследования, не полная переходная цепочка `CANDIDATE/CONFIRMED/INVALIDATED/EXPIRED/WAIT`. Нужны иммутабельные T0, версия параметров, уровень отмены, горизонт и запись будущего исхода отдельно.
6. **Метаданные инструмента**: tick_size, tick_value, multiplier в `CONTRACTS` пока пусты; их нельзя выдумывать. Нужен проверенный официальный источник и исторически корректная единица.
7. **Доступность внешних источников**: официальная документация MOEX ISS описывает delayed/подписные сделки; `ALGOPACK FO tradestats` содержит агрегированные `vol_b/vol_s` по пятиминуткам, но его подписной доступ здесь не подтверждён, и этот агрегат **не** заменяет полный trade-level price profile. Никакой оплаты или обхода доступа.

## Очерёдность работ на существующем MCP / GitHub

**P0. Контракт и аудит.** Эта версия + машинный манифест всех 87 правил; в `STORAGE_RULES` сохранять только ссылку/качественные ограничения. Никаких новых книг/вкладок/секретов/второго сборщика.

**P1. Source quality и PIT.** В существующем Google-first archive и общего MOEX клиента:
  - read-only `archive.model3_coverage` расширить до **поля/источника/контракта/дня/причины пропуска**, без заявления `PASS` по длине таблицы;
  - независимый аудит SHA, OHLCV, H1/M15 и session rule ↔ первичный биржевой trade date; отдельные ERROR/UNKNOWN;
  - для новых наблюдений дополнить provenance/receipt только после отдельного schema-review: source-published, observed-at, feature-calculated, exact version, source digest. Старую историю не переименовывать PIT;
  - сохранить точные контрактные значения OHLCV и первичные ZIP; повторный источник не вызывать для заполненных проверенных ключей.

**P2. Общие числовые признаки из уже хранимых данных.** Детерминированно рассчитать только отсутствующие/некорректные **2026** OHLCV-признаки в существующих `*_INDICATORS`, с прогревом, версиями, проверкой T−1, exact SECID и readback. Исполнение через существующий `model3_google_backfill` или общий registered feature engine; **не** создавать альтернативный collector. До анализа целевых полей и тестов 95-колоночной записи ничего не менять.

**P3. Дополнительные потоки (независимый gate).** Проверить права и историческое покрытие реальной Delta/Volume-at-Price. Добавлять `*_exact` только при фактическом источнике, масштабе времени, unit, trade-side semantics, SHA и объёмной сверке с OHLCV. При отсутствии источника: `NOT_AVAILABLE`, не искусственный результат. Старые approximate поля сохранять и не смешивать.

**P4. Исследовательское событие.** После P1/P2/P3: собрать фиксированный `feature_snapshot` на закрытом H1 с завершённым D1; версионированные условия 87 правил и независимый outcome журнал. Допуск прогнозов и статистика **только отдельно** после OOS/качества. Никогда не отправлять `forecast.create` в ходе подготовки данных.

## Техническая приёмка первого кодового этапа

- GitHub PR **Draft**, изолированная ветка; не merge/deploy/schedule/production database/secrets/реальные торговые операции.
- Никаких изменённых RAW-свечей, существующих ZIP, старых 95-колоночных строк и старого Forecast 18082.
- Тесты: coverage = key-based, missing vs zero, incomplete source, old calendar, late/unknown available_at, future look-ahead, cross-SECID, duplicates, M1-profile exact-vs-proxy, repeated readback/no-op, no unapproved external calls.
- Для новых полей требуется отдельная утверждённая совместимая схема по именам + тесты читателя и единственного писателя + обратное чтение живой книги под контролем владельца. Пока этот gate не пройден: **no schema mutation / no data write**.
- HOME acceptance требует доступа к живому порту 18085, installed source SHA и tools/list, а не только GitHub CI. HOME probe из текущего чата вернул 429; статус процесса **не подтверждён**.
