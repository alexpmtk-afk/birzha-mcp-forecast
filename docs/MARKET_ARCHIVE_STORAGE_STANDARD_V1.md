# Единый стандарт хранения рыночной истории v1 (31.10.2026)

**Статус документа:** предложенный общий контракт, зафиксированный в GitHub; до отдельной реализации и установки на HOME не считать новым исполняемым функционалом MCP. История не перезаписывается; merge/deploy/запуск сбора этим документом не разрешаются.

## 1. Область и источники истины

Инструменты проекта: `SBER`, `Si` (фьючерс доллар–рубль), `BR`, `GOLD`, `IMOEX`, `RI` (фьючерс РТС). Индекс `RTSI` исключён из активного маршрута, старые индексные данные сохраняются отдельно. Биржевой идентификатор — **точный SECID**, для фьючерсов обязательно различать контракты `RIH6`, `RIM6` и т.п.

Порядок доказательств: (1) исходный ответ MOEX/допустимого провайдера с точным SECID; (2) неизменяемый исходный файл и манифест с контрольной суммой; (3) рабочий серверный архив с проверенным обратным чтением; (4) каноническая Google-книга и протокол сверки. GitHub — источник кода и контракта, а не сам факт установки на HOME. Google-книга и DuckDB не должны молча объявляться синхронизированными.

## 2. Одна книга и две служебные папки на инструмент

Родительский путь: `Мой диск / Биржа / Архив рыночных данных / <папка инструмента>`.

* `MOEX_HISTDATA_<SYMBOL>_MCP_CANONICAL` — единственная действующая каноническая книга инструмента. Содержит D1/H1/M15, индикаторы при подтверждённом источнике и существующие служебные вкладки. Не создавать дополнительную книгу на каждый импорт, не удалять/переименовывать существующие вкладки ради унификации.
* `01_M1_SOURCE/` — **один канонический исходный архив на ключ `(exact SECID, YYYY-MM)`**. В нём должны сохраняться все наблюдаемые M1 с реальными ценами и объёмами, входной manifest/provenance, а также проверенные дополнительные D1/H1/M15 при наличии. Не создавать дубликаты `RAW`/`SOURCE` под разными именами.
* `02_LEGACY_AND_RECOVERY/` — старые результаты исследований, подтверждённые резервные копии и исторические повторные загрузки до отдельного аудита/решения об удалении. **Не основной источник** для новых расчётов.
* Отдельные временные папки на Диске и новые листы на каждую выгрузку запрещены. Staging/временные артефакты — в изолированном рабочем окружении с ограниченным сроком жизни. Удаление исходников допускается только по отдельному утверждённому плану после проверки ссылок, SHA и обратного чтения.

**Реально выполнено только для RI:** [папка RI - Фьючерс РТС](https://drive.google.com/drive/folders/1v0ZYWbxp5vuH8WIuQtTcg6qBfX1b69Ez),
[01_M1_SOURCE](https://drive.google.com/drive/folders/1xFnh43h-Lbjf9GoNTcVAXIet3Fsr5vQG),
[02_LEGACY_AND_RECOVERY](https://drive.google.com/drive/folders/1pHJSw_IzqxzqPUHAHGiCur0rpwUK1fb0),
[MOEX_HISTDATA_RI_MCP_CANONICAL](https://docs.google.com/spreadsheets/d/1PuPv7Nv_Dpj-KTECPHNHecj34HrR9K5y53OwRcu7RVY/edit).
В RI-книге используются `M1_SOURCE_INDEX` (каталог источников; M1 **не загружены как отдельные строки Sheets**) и `STORAGE_RULES` (пояснения). По состоянию передачи: 16 архивов источника, 232613 наблюдаемых M1 (OHLCV), 31 объект в legacy, 0 дубликатов минутных ключей внутри проверенных источников. Это **не** официальная календарная/PIT-аттестация. Для остальных пяти книг — будущий шаблон, **папки и миграция не подтверждены**.

Важная RI-специфика: ранее удалённый `README_STATUS` намеренно **не восстанавливать**. Синхронизация в `SYNC_STATUS`, качество в `QUALITY_AUDIT`, `SESSIONS` не заполнять ложными подтверждениями.

## 3. Контракт M1 и объёма

Гранулярность: **один реальный минутный бар `(exact SECID, begin_msk)`**, в UTC/Moscow использовать однозначное время с часовым поясом. Обязательные исходные поля: `secid, begin, end, open, high, low, close, volume, source_id`. По источнику дополнительно хранить `turnover/value` при наличии, `capture_at`, `source_url`/query interval, `provider`, `retrieval_version`, `raw_sha256`, `availability_confidence`, качество и полноту.

`volume` означает **количество контрактов или акций за минуту, согласно единице конкретного инструмента**, а не цену и не разницу числа сделок. Если объём для индекса (например, IMOEX) неприменим, записывать `NULL`/N/A с причиной, не ноль. Для MOEX `begin/end, OHLC, volume` брать из самого ответа; не восстанавливать объёмы из цен и не создавать синтетические минуты.

**Вертикальный объём** за период — сумма `M1.volume` соответствующего **одного** exact SECID и корректно установленной торговой сессии, когда источник и единицы сопоставимы. M1 OHLCV **не** даёт объём по каждой конкретной цене внутри минуты, агрессорскую дельту и точный горизонтальный профиль: для этого нужны сделки/статистика потока с отдельной аттестацией.

M15 агрегировать только из наблюдаемых M1: `open` первого, `high` максимум, `low` минимум, `close` последнего, `volume` сумма. Если минут не 15, бар **SPARSE/INCOMPLETE**; не выбрасывать реальный объём, не заполнять искусственными нулями, не выдавать за полностью наблюдаемый интервал. Исходные D1/H1 не заменять без доказанного равенства. Границы MOEX торгового дня, night/extra sessions, клиринги, rollover и историческая доступность данных требуют отдельной проверки.

Фьючерсные контракты в один ряд цен не соединять на этапе RAW. Контракт для исследования непрерывной серии выбирается по **T−1**-правилу на основании уже завершённой сессии; RAW/Forward/Additive/Ratio хранятся/рассчитываются раздельно. Не суммировать одновременные RIH6+RIM6 и другие контракты как единый объём выбранного RI.

## 4. Manifest и недопущение дубликатов

Ключ файла `(SYMBOL, exact SECID, YYYY-MM)`, имя `<SYMBOL>_<SECID>_<YYYY-MM>_SOURCE_M1_OHLCV.zip`. **Внутренний** `manifest.json` содержит: `schema_version`, `symbol`, `secid`, `period`, `source`, `capture_at`, `first_m1`, `last_m1`, `m1_rows`, `m1_volume_total`, `payload_sha256`, `quality_status`, `trade_calendar_status`, `pit_status`, `provenance`; отсутствующее помечать UNKNOWN. **Внешний реестр** (`M1_SOURCE_INDEX`/серверная БД) после окончательного сохранения ZIP содержит `zip_sha256` (SHA-256 реально сохранённых ZIP-байтов), `source_file_id` и ссылку на конкретную ревизию. Нельзя помещать SHA полного ZIP внутрь него самого: это создаёт самоссылку; не путать `archive_sha256` у старых архивов (часто SHA JSON-payload) с `zip_sha256`. Для старых архивов трактовать существующий SHA строго согласно полю манифеста и проверить его на фактических байтах.

Нельзя выдавать неизменённый файл под новой датой или другим именем как новый источник. Перед загрузкой проверять ключ и реально сохранённые байты SHA256. При совпадении — NOOP и журнал. При отличии — сохранить доказательство версии/ревизии и провести приёмку перед заменой; без молчаливой перезаписи `source_file_id`. Не удалять объект, который упоминается в `source_file_id` существующих свечей, пока ссылки не перенесены и проверены.

## 5. Порядок обновления и обязательные проверки

1. Выяснить контур (рабочий HOME/DuckDB, GitHub исследование, Google зеркало), реальные права и текущие coverage/manifest. Различать статус **DOCS_ONLY**, **GITHUB_MAIN**, **HOME_INSTALLED**, **DATA_VALIDATED**.
2. Проверить даты, точный SECID, завершённые сессии; скачать только отсутствующее в пределах запроса и API-governor. При повторе без пропусков должен быть NOOP.
3. Во временной области проверить сортировку и уникальность `(secid,begin)`, OHLC, неотрицательный volume/NULL policy, непрерывность доступных минут (gap отдельно), checksum и локальную корректность M15/H1.
4. Зафиксировать источник и manifest **один раз**; обратным чтением проверить сохранённые байты, SHA, строки, суммарный volume и ссылки.
5. Только после этого, при явно разрешённом writer и без конкурирующего зеркала, продолжить запись/сверку D1/H1/M15 и зависимых полей, обновить `QUALITY_AUDIT`, `SYNC_STATUS`, каталог M1. Никогда не подтверждать успех до чтения результата.
6. При ошибке оставить прежний подтверждённый архив, оформить BLOCKED/PARTIAL с конкретным диапазоном; повторить только недостающую порцию. Временные файлы удалить лишь после PASS и сохранения provenance; удаление legacy отдельно согласуется.
7. Не выполнять новые исторические сборы, merge, HOME deploy, production DB/secrets без разрешения на соответствующее действие. Документ сам не запускает расписание.

## 6. MCP и GitHub: статус реализации (не путать)

* Существующие `history.coverage`, `history.stored_series`, `history.sync`, `archive.contract`, `archive.collect`, `archive.update`, `archive.sync` применяются только если реально установлены и доступны на конкретном HOME. У вызовов разная семантика и право записи. Старый HOME может не содержать `archive.*`. Ни одна из команд **не удостоверяет сама по себе**, что новые ZIP-названия, M1-каталог и idempotent storage v1 уже реализованы.
* В текущем GitHub `src/birzha/storage/model3_minute_archive.py` уже реализован **локальный RI-only** `MinuteArchiveCapture`: ZIP по `(RI exact SECID, SHA содержимого, произвольный диапазон)` и повтор того же payload возвращает NOOP; код подключается как `_minute_observer` в `moex_iss.py` при M1-запросах. `src/birzha/application/model3_minutes.py` умеет читать и проверять такие ZIP. Это **не** один Google ZIP на `(SECID, месяц)` и не общий сервис M1 для шести инструментов. Новый слой должен использовать существующий захват/проверки, не ломать локальную content-addressed историю, не создавать второй MOEX-загрузчик. Нельзя трактовать имя, включающее SHA, как календарный ключ или автоматически удалять более ранние версии.
* До утверждения server writer различать `STAGING_BATCH` (локальные захваты частей месяца), `CANONICAL_MONTH` (единая опубликованная версия) и `HISTORICAL_REVISION` (сохранённая при исправлении/переиздании версия, без потери provenance). В частично прошедшем месяце допустимы промежуточные новые данные, но в `01_M1_SOURCE` должен быть **один активный месячный объект**; полная атомарная сборка и проверка предшествуют замене, старый объект сохраняется в recovery/версионной истории. Установка на HOME отдельно разрешается.
* Для полноценного сервера требуется отдельная **реализация** адаптера источников/каталога M1 (read-only перечисление и чтение exact SECID/date, volume), проверка и идемпотентный writer + manifest, и план миграции legacy без удаления истории. Названия будущих MCP-команд до утверждения API **не фиксировать как существующие**.
* В репозитории `msp-server-bridge` есть отдельный исследовательский сборщик `research/ri_contract_month_capture.py` и GitHub Actions с артефактами; это не запись HOME и не гарантированный upload в Drive. Изменение сохранения исходников в GitHub исследовательском контуре — отдельная задача с тестами.

## 7. Условия PASS для будущего внедрения

На одном точном SECID и месяце доказать: повторный запуск не создаёт повторного ZIP; M1 OHLCV совпадают с MOEX-источником; общее число минут и сумма volume равны manifest и обратному чтению; `source_file_id` валиден; ошибки ввода/потеря сети безопасно прерывают запись, без разрушения старых данных; индикаторы не выдают закрытый/отсутствующий источник за 0; HOME SHA и MCP tools доступны после отдельно разрешённого deploy.

Пока выполнено **только организационное приведение RI Google Drive + каталог M1**. Серверный runtime и ещё пять инструментов по этому стандарту не мигрированы.
