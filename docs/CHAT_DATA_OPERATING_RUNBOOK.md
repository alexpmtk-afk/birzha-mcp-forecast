## 1. Сначала определить доступ, затем выбрать маршрут

GitHub хранит код, инструкции, задания и отчёты. Само подключение GitHub не
подключает программу на компьютере владельца и не запускает её команды.
Нельзя обращаться к localhost компьютера владельца из облачного окружения:
там localhost означает компьютер самого облачного окружения.

| Что действительно доступно чату | Действия | Граница результата |
|---|---|---|
| GitHub и Google Drive, без сервера и среды выполнения | Читать main/инструкции, проверять доступные архивы/таблицы, готовить конкретное задание исполнения по разделу 5 | Подготовка и доступные проверки выполнены; серверная операция ожидает исполнения |
| Среда с Python или разрешённый GitHub Actions, без HOME | Проверять точный код, работать с разрешёнными изолированными копиями и собирать источник в пределах задания | Результат относится к этому окружению; не является записью в HOME |
| Подключённые команды сервера Биржи | Читать правила и покрытие, проверять данные; загрузку выполнять только в разрешённом объёме | Можно подтвердить фактическое серверное чтение/загрузку по ответу |
| Локальная среда с разрешённой программой управления HOME | Исполнять подготовленный запрос через штатный контур и публиковать обезличенный результат | Подтверждается фактический результат конкретного задания |

Один раз изучи перечень реально доступных инструментов. Если history.* нет,
не пытайся многократно вызвать выдуманный инструмент и не требуй от пользователя
обязательно подключить сервер. Сразу продолжай доступную часть и используй
маршрут задания на GitHub ниже. Не делегируй обычное чтение кода и диагностику.
Если нет права записи на GitHub, подготовь полностью заполненное задание в
ответе; явно укажи, что оно ещё не опубликовано. Не утверждай, что его приняли.

## 3. Если сервер подключён

Проверить tools/list и вызвать history.session_rules({}). Сверить
installed_source_sha с нужной версией; опубликованный SHA не доказывает текущую
установку. Отсутствующая команда — ограничение окружения/версии, не ошибка цен.

Пример чтения, которое само не загружает MOEX:

```json
{"tool":"history.coverage","arguments":{"secid":"RIH7","timeframe":"H1"}}
```

```json
{"tool":"history.stored_series","arguments":{"secid":"RIH7","timeframe":"H1","from_date":"2026-10-09","till_date":"2026-10-14"}}
```

Форма выше — имя и аргументы MCP-вызова, не команда shell и не HTTP-адрес.
Повтори отдельно по D1/H1/M15. stored_series допускает максимум367 календарных
дат включительно и50000строк; длинный архив читать ограниченными окнами.
Даты фильтруют исходный begin, не независимо аттестованную торговую дату.
Границы coverage и число строк не доказывают отсутствие внутренних пропусков.

Только если установлены недостающие диапазоны и их сбор разрешён:

```json
{"tool":"history.sync","arguments":{"symbol":"RI","timeframe":"H1","from_date":"2026-10-12","till_date":"2026-10-14"}}
```

Это пример формы, не поручение заново загрузить указанные даты. history.sync
пишет в назначенное хранилище; stored_series только читает. Не заменять sync
вызовом market.candles в расчёте на автоматическое постоянное сохранение.
Сохранить ответ операции, затем вновь проверить покрытие и фактические строки.
Не запускать общий sync_core ради задачи одного инструмента.

Для Si/BR/GOLD загрузчик history.sync принимает корень symbol и сам разделяет
историю по контрактам через существующий исторический resolver. В coverage и
stored_series нужен точный secid каждого контракта. Текущий активный контракт
из market.resolve_active_future не является разрешением старого периода.
При отсутствии доказанной карты исторических контрактов остановить эту часть,
зафиксировать неизвестность; не подставлять сегодняшнюю серию за два года.

## 4. Сбор, формирование, соединение и проверка

1. До запроса: инструмент/SECID, рынок/режим торгов, периоды и даты, существующий
   принятый диапазон, точный код, цель, источник, временный и конечный адреса.
2. Проверить существующие файлы/ключи, SHA и предыдущую приёмку. Принятый архив
   не скачивать заново только потому, что у текущего чата нет доступа к HOME.
3. Использовать существующий загрузчик и общий ограничитель запросов. Страницы,
   повторы и Retry-After обрабатываются штатным кодом; не обходить ограничения
   прямыми параллельными запросами. Внутридневные порции ограничены существующей
   политикой до трёх торговых сессий; сохранять каждую принятую порцию и курсор.
4. D1 и H1 получать как соответствующие исходные свечи. M15 строится из M1 по
   существующей версии алгоритма. Строгая полная четверть требует15 разных
   последовательных завершённых минут. Нативный/сессионно укороченный бар и
   сохранённый completed сами этого не доказывают. **Не выбрасывать** реально
   наблюдавшиеся минуты из архива только потому, что их меньше 15 в четверти:
   сохранять отдельно разреженный M15 с точным числом наблюдавшихся M1,
   признаком SPARSE, неизвестной причиной пустых минут и исходным объёмом.
   Не считать sparse автоматически допущенным к Модели №3; для строгого расчёта
   отбирать DENSE_15_OBSERVED и только реально завершённые, доступные свечи.
   H1 с исходным end раньше конца часа не объявлять незавершённым только
   по его длительности: отделять source_span от закрытия интервала и available_at.
5. Соединение между сессиями — чтение одного SECID/периода по времени через
   load_exact/store.read. Сохранить исходные OHLCV, NULL, времена, версии,
   происхождение и реальные разрывы. Не сдвигать цены, не заполнять ночи и
   выходные, не объединять неполный интервал со следующей сессией, не соединять
   разные контракты. Не писать второй независимый алгоритм поверх существующего.
6. Проверить идентичность, даты, порядок/перекрытия, уникальность ключей,
   конфликтующие цены, OHLC, объёмы/NULL, неполные и отсутствующие интервалы.
   Ключ SECID/timeframe/begin не заменяет сравнение содержимого. Конфликт
   изолировать, а не замалчивать последней записью. Известные вопросы выбора
   версий старого reader не считать решёнными новой командой чтения.
7. civil_date и trade_session_date различать; исторические available_at и
   first_seen не выдумывать. Соединённый ряд не получает автоматически допуск
   Forecast, доказательство календаря или точности модели.
8. Сохранить пакет исходных ответов/происхождение, SHA, перечень файлов, диапазоны,
   количества и ограничения в постоянном архиве по заданию. Временный GitHub
   artifact имеет срок хранения и не заменяет постоянный архив. Если исходные
   M1 не сохранены, явно отметить невозможность независимой пересборки M15.
9. Зеркало Google — отдельный этап принятые серверные/исследовательские данные →
   разрешённый экспортёр → существующая книга → чтение обратно. Отсутствие
   экспортёра не исправлять созданием новой книги или обратной загрузкой ручных
   правок в сервер. При обрыве прочитать записанные ключи перед продолжением.
10. Обновить реальную приёмку в Карте; сообщать отдельно сбор, серверную запись,
    облачную выгрузку, проверку календаря и допуск модели. Успех одного не означает
    успех другого. При отсутствии доступа к Карте подготовить точную запись,
    не заявлять, что она уже внесена.


## 4A. Разные фьючерсные контракты: T−1 selector в main, continuous ряд отдельно

Для перехода между `RIH6→RIM6`, `RIM6→RIU6` и подобными контрактами
не использовать правило раздела 4 о соединении сессий одного SECID.
В исходном GitHub main исторический resolver `moex_history.py` **уже использует
общий `continuous_futures.py` — объём предыдущей завершённой торговой даты T−1
с защитой по официальной дате окончания контракта**, исключением спредов,
неизвестных дат и объёмов. Версия выбора: `MOEX_T_MINUS_1_VOLUME_EXPIRY_V1`;
история, проверенная старым критерием, не принимается после повышения поколения
`ROLLING_HISTORY_V3_T_MINUS_1_EXPIRY`.

Однако `market.candles(root,from,till)` по-прежнему возвращает свечи **одного
SECID**, а не многоконтрактный непрерывный ряд с Additive/Forward/Ratio.
Для математических правил и ещё незакрытых тестов читать
[CONTINUOUS_FUTURES_POLICY_RESEARCH_20261029.md](CONTINUOUS_FUTURES_POLICY_RESEARCH_20261029.md)
и [FUTURES_RUNTIME_RESOLVER_STATUS_20261029.md](FUTURES_RUNTIME_RESOLVER_STATUS_20261029.md).
Нельзя утверждать, что многоконтрактные данные доступны в Forecast, пока
отдельно не подтверждён их интерфейс и схема price coordinates.
RAW остаётся по точному SECID. `available_at` исторической загрузки
всё ещё не доказывает first_seen в момент прогноза. HOME также требует
отдельного чтения installed SHA; GitHub/CI не устанавливает локальный runtime.

## 5. Маршрут через GitHub без прямого HOME-доступа

В проверенном контуре на15.10.2026 нет подтверждённого автоматического обработчика
GitHub issue → HOME. Локальная программа управления читает локальную очередь,
а не GitHub. Создание issue/PR/файла в control само не запускает сервер.
Не писать секреты, токены, приватные ответы или сетевые адреса управления в issue.

Использовать GitHub как прозрачную передачу конкретного задания:

1. Найти существующую карточку инструмента в Карте и связанный issue/PR. Продолжить
   его, не создавать дубликат и конкурирующее решение.
2. При необходимости создать issue по шаблону «Исполнение рыночных данных»
   (Issues → New issue). Это техническая передача, не новая оперативная очередь.
   Если запись другим людям требует согласия, подготовить текст до его получения.
3. Заполнить инструмент/контракт/период/даты, код и архив с SHA, уже выполненные
   проверки, разрешённые действия и точные вызовы. Если нужна только проверка,
   передать только читающие вызовы, без sync и без установки.
4. Исполнитель — локальный инженер проекта с доступом к штатному управлению
   HOME; назначение сверяется с Картой. Веб-чат не изображает этот доступ.
   Пользователь не должен вручную писать команды или выяснять параметры.
5. Локальный исполнитель читает тот же issue и выполняет только разрешённый
   объём через существующий контролируемый канал. Merge/deploy/restart,
   изменение production и доступ к секретам требуют отдельного решения.
   Поручение коллеге само по себе не предоставляет эти полномочия.
6. Исполнитель публикует в том же issue безопасный результат: фактический SHA,
   время/окружение, ответы/сводку команд, количества до/после, SHA архива,
   ошибки и недоказанные условия. Отсутствие ответа не считать исполнением.
7. Автор проверяет соответствие результату задания и обновляет приёмку Карты.
   Существующие ссылки дают воспроизводимую историю без переписки по кругу.

GitHub Actions допускается только при наличии реально доступного workflow с
подходящими параметрами и разрешения на его запуск/сеть. Стандартный GitHub
runner не видит HOME и не обновляет его без отдельно установленного канала.
Например .github/workflows/g2-six-market-source-receipt.yml собирает отдельные
непроизводственные исходные ответы, не является универсальной очередью архива
одного инструмента и не устанавливает их в HOME. Обычный CI — проверка кода.
Не запускать случайный workflow вместо недостающей серверной операции.

Если исполнитель или способ передачи не назначены, зафиксировать один конкретный
инфраструктурный блокер и готовое задание. Проверки GitHub/Drive продолжать.
Не требовать подключения MCP от каждого веб-чата как единственного варианта.

## 6. Форма задания и отчёта

```text
Карточка Карты / существующий issue:
Инструмент и точный SECID (либо что ещё нужно разрешить):
Цель: проверка / недостающая загрузка / исследовательский перенос / зеркало
Окружение исполнения и ответственный:
Код: repo, ветка, точный SHA; зависимые PR:
Периоды и даты; гражданские или подтверждённые торговые:
Принятый архив: постоянная ссылка, SHA-256, количества, источник приёмки:
Назначение: база/книга/лист (из памятки09), без секретов:
Уже сделано и что именно остаётся недоказанным:
Разрешение пользователя и границы; какие изменения запрещены:
Точные команды/аргументы; чтение отдельно от записи:
Ожидаемый результат и проверки неизменности:
```

Исполнитель отвечает по этим же полям, дополнительно: время, фактический SHA,
ответ операции, количество строк/границы/исключения/конфликты, куда сохранено,
чтение обратно, ошибки/ограничения. Статусы «подготовлено», «ожидает исполнения»,
«выполнено», «проверено» различать; не повышать статус только по обещанию.

## 7. Границы актуальной приёмки и самостоятельность

15.10.2026 принята установка #245 SHA035735f83a76bc932391109f046b20a05db80afb:
38команд, чтение SBER09–14.10 D1/H1/M15=4/72/276 и одинаковые повторы.
Это датированное доказательство чтения SBER, не полнота RI и не вечная
гарантия состояния сервера. #244 облачной выгрузки отдельно не установлен.

Работай самостоятельно в доступной среде, используя эти правила. Не спрашивай
повторно про смысл соединения свечей, каноническую книгу, обычную порцию или
ранее данное разрешение. Эскалация только по отсутствующему доступу/исполнителю,
неразрешимому существенному противоречию или выходу за полномочия. После2–3
неудач одного подхода — факты и конкретное необходимое действие, без повторов.

Итог: чат сам выбирает доступный маршрут, готовит полное задание при необходимости
локального исполнения и принимает результат по доказательствам. Чтение GitHub,
исполнение на сервере и перенос в облачную таблицу фиксируются раздельно.
