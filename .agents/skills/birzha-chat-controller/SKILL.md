# Контроль чатов Биржи
Версия 1.0, 29.10.2026. Объявить применение навыка. Навык не расширяет полномочия.

## Вход и цель
1. Проверить последнее указание владельца и состояние паузы. Пауза запрещает новые обращения исполнителю; отдельное разрешённое расследование допустимо.
2. Зафиксировать полную цель, инструмент/период, место результата, обязательные требования, приёмку, полномочия, ближайший измеримый результат, исполнителя и срок следующей проверки. Пилот не заменяет полную цель.
3. Проверить рабочую папку, ветку/SHA, состояние дерева, свежесть GitHub main и открытые PR. Старую origin/main не считать актуальной без проверки. При отсутствии доступа отметить неизвестность; не удалять чужие файлы для ремонта Git.
4. Читать применимые AGENTS.md и docs/CHAT_DATA_OPERATING_RUNBOOK.md из проверенной версии. Для Модели 3 дополнительно прочитать соседний birzha-model3-data/SKILL.md. Не полагаться только на память чата.
5. Проверить отдельно доступ к источнику, результату коллеги, чтению назначения и разрешение записи. Справочник не доказывает получение свечей. GitHub не означает доступ к HOME.

## Каждый содержательный цикл
- Проверить новое завершённое сообщение после ожидаемого запроса. Старый ответ, idle, updatedAt не означают новый результат. Один ожидающий запрос на чат; подтверждённую отправку без ID сохранить по маркеру и не повторять.
- Прочитать результат и независимо проверить относящиеся к этапу факты. При недоступном тексте один раз организовать передачу собственного отчёта исполнителя в согласованное место.
- Учесть отдельно прирост данных и доказанных фактов. Новый заголовок этапа, повтор ошибки и программа без успешного запуска не подтверждают работоспособность.
- При первой ошибке использовать [диагностику](references/diagnostic-protocol.md). Проверенное исправление передавать с воспроизводимым примером; непроверенное действие явно назвать диагностическим опытом.
- После двух завершённых циклов без результата и нового доказанного факта обязательно пересмотреть подход. Счётчик не сбрасывать после переименования этапа или восстановления контекста. Ожидание не увеличивает счётчик; превышение срока ожидания требует одной проверки препятствия, не повторной отправки.
- Перед новым поручением вызвать scripts/control_gate.py с отдельным состоянием задачи по [схеме приёмки](references/acceptance-checks.md). REPLAN требует записанного изменения подхода; PAUSED/WAIT/NO_NEW_RESULT/BLOCKED запрещают обычную отправку. REVIEW означает необходимость аудита, не разрешение записи или автоматической отправки.
- Поручение содержит проверенные факты, дефект, одно действие, точные входы, ожидаемый результат/место, предел проверки, условия остановки, доказательства приёмки.
- После подтверждённой отправки сразу сохранить маркер, ID при наличии и ожидание. При неизвестной доставке проверить её прежде повторной отправки.
- Отчёт владельцу: «Что сделано» и «Что нужно сделать» простым русским языком. В неизменном периодическом ожидании молчать, если пользователь не просил иначе.

## Завершение и восстановление
Принимать по [доказательствам](references/acceptance-checks.md). Частичный результат не закрывает цель; обязательное недоступное остаётся незакрытым. Хранить состояние отдельно: цель/версия, ответы, запрос, доказательства, причина сбоя, попытки, счётчик, следующий шаг/срок. Не публиковать приватную переписку, секреты и рыночные архивы в публичном репозитории.
При восстановлении читать состояние и только изменившиеся источники. Наблюдение после паузы само не возобновлять. [Испытания](references/evaluation-cases.md) должны проверять решения, а не заголовки текста.

## Переходы
Перед первым поручением использовать initial_request=true при нулевой истории попыток: START_REVIEW требует проверки полномочий и конкретного задания.
При завершении ожидаемого запроса сначала проверить связь ответа с маркером, сохранить ответ и снять ожидание; затем проверять следующий шаг. replan должен относиться к текущему cycle_id, старый план не переносится автоматически.
